MODULE 22 Evidence

How To Test An Edge

Testing an edge is not a search for proof that an idea pays: it is an arrangement, built before you look, that gives the data every fair chance to say no.

Copies this lesson as Markdown to paste into any AI assistant

The Backtest That Looked Like An Edge

You had an idea, you pulled up a few months of charts, and it looked good. So you adjusted the stop a little, skipped the Mondays that went wrong, and ran it again. Now it looks very good. And when you trade it, it does nothing of the kind, and you cannot tell whether the idea was wrong, the test was wrong, or you were.

Almost always, the test was wrong, and in a specific way: it was built so it could only say yes. Module 01 named the standard: a rule locked before the data, a null, split samples, and your own executions counted apart. This page is the workshop version. It shows you how to run each step on a rule of your own, what the report must contain, the two gates you hold your own register to, and the label each idea earns. Seven parts, mechanical first: the locked paragraph, the null, the splits, the report, the gates, the simulator, and last the hardest one, the label you give an idea you like.

Register (Hypothesis Register)
Your own written list of trading ideas under test. Each entry carries a number, the locked rule paragraph, the date it was locked, its test results in R, its gate results, its label and, if it failed, the reason and a reopen condition.

Lock The Rule In One Paragraph

Before you download a single bar, write the rule as one paragraph with five parts: the rule (what has to be true), the entry (the exact price and moment the order goes in), the stop, the target, and the window (the hours it may fire, and the date range of the data). Add the costs you will charge each trade and the way you will build the null. Date it. Save it somewhere you cannot quietly edit.

Locked Rule
A rule written in full, and dated, before the data that tests it is opened: rule, entry, stop, target and window in one paragraph, plus costs and the null. Any change after the data is seen is a new rule with a new register entry.

A paragraph that passes looks like this: "Between 10:00 and 11:30 ET, when [condition], enter at the open of the next 1-minute bar. Stop [where, behind what]. Target [the structural level]. One trade per session. Any trade still open at 12:00 ET is scored at that price. Data: [first date] to [last date]. Costs: one round-turn commission and one tick of slippage per side, in R. Null: the same rule on 1-minute returns shuffled within 30-minute blocks." If someone else could code your paragraph without asking you a question, it is locked. If they would need to ask "what counts as a strong bar?", it is not.

Three habits keep the lock honest. Test the rule with the stop you would actually trade, behind structure, not a stopless version with a stop chosen later from the results. If you want to try variants (two stop placements, two windows), try them on an early training stretch only, lock the one you pick, and score it on data it has never seen. And a filter you think of after seeing results ("skip Mondays") is a new rule with its own entry and its own test; it never edits the locked one. Even then, a backtest is an upper bound: it takes every signal, at the stated price, with no hesitation, and you will not.

The rule: the paragraph is written, dated and saved before the data is opened, and the test runs exactly what it says.

Getting it wrong looks like a first run, a look, then a "small fix" to the stop and a second run reported as the result. What it reveals: you are searching for a version that would have looked good, and a version fitted to the data always looks good on that data. The fix: give each paragraph an entry number and a date, and save it before you download anything. Any edit, however small, gets a new number and starts its own test from scratch. Your register shows the edits as separate rows, so the count of tries is visible.

Run The Same Rule On Shuffled Data

A result means nothing until you know what the same rule earns when there is nothing for it to find. That comparison is the null, and the honest version of it, in plain words, goes like this.

Null (Block-Shuffled Null)
The same locked rule run on price paths rebuilt from each session's own 1-minute returns, shuffled within 30-minute blocks. Shuffling destroys any real sequence while keeping the session's volatility. Its average expectancy across many shuffles is the baseline the rule must beat.
  1. Take one session of 1-minute bars and turn it into a list of 1-minute returns: how far each minute moved from the last.
  2. Cut the session into 30-minute blocks: 09:30 to 10:00, 10:00 to 10:30, and so on.
  3. Inside each block, shuffle the order of the minutes. The block keeps every move it had; only their order changes.
  4. Rebuild a price path from the same opening price, and run the identical rule on it: same entry, same stop, same target, same window, same costs.
  5. Do it for every session in the data, then repeat the whole pass many times (two hundred is a workable number) and average the results. That average is the null's expectancy.

Why within blocks: the most obvious fact about intraday data is that big bars follow big bars. The first half hour is wild, the lunch hour is quiet. Shuffle the whole day and the open's violence ends up at lunch, every session looks like nothing real ever does, and your rule beats a null that was never a fair opponent. Shuffling inside 30-minute blocks keeps the open wild and the lunch quiet, and removes only the one thing your rule claims to read: the order in which things happen.

That is why "beats random" is the only honest baseline. Zero is not one: a rule run on random paths can earn positive R from a drifting market or from where its stop and target sit, and lose it from costs. Fifty percent is not one either: a rule with a tight stop and a distant target wins less than half the time on random data by construction. The null charges your rule for everything the market and your geometry would have given it anyway.

The rule: every result is reported beside the null's result, built by the same code on block-shuffled data, and the rule counts only by what it earns above the null.

Base rates show the size of the trap. In TradingStats' NQ initial balance data (3,163 sessions, as compiled in the TradingStats source of truth, updated 2026-06-08), the initial balance breaks on at least one side in 95%+ of sessions. A rule scored "right" whenever price leaves the first hour's range would be right on nearly every day of the sample, and almost none of that would be the rule. The base rate is the market doing what it does; the null is how you measure it for your exact rule.

Getting it wrong looks like "positive expectancy" with no comparison, a rule compared with a coin flip, or a null built by shuffling whole days. What it reveals: you chose the comparison that flatters the rule, which is the same as not testing it. The fix: the null goes in the locked paragraph (block length, number of shuffles), and the report template has a null column that cannot be left blank. If the rule beats zero but not the null, the report says so in those words.

Both Halves, Every Year, Then The Recent Stretch

A pooled result can hide two opposite stories. Suppose a made-up rule shows +0.12R per trade over 200 trades. Split it in time order and the first 100 trades show +0.30R and the second 100 show −0.06R. The pooled figure describes neither half. It describes one good stretch and one bad one, and you cannot tell which is the exception.

So the result is cut three ways, all in time order and all named in the locked paragraph:

  • Both halves. The trades split at the middle by count, first half and second half. Never a random split: random halves mix the years and hide exactly the change you are looking for.
  • Every calendar year. One row per year, with its own n, result and null. One extraordinary year can carry a whole sample; the year rows show you whether it did.
  • The recent stretch, last. For a test run now, 2023 to 2026, read on its own. It weighs most, because it is closest to the market you will trade. If the rule fails here, the market it was measured in may no longer exist, and the older years are history rather than evidence.

The rule: the rule must beat its null over the whole sample, and be positive in both halves, in every calendar year and in the recent stretch. Show the null beside every cut, so you can see where the margin thins. A single cut that fails is a failure of the whole result, not a footnote.

Getting it wrong looks like dropping 2022 because "that was an unusual year", or trying splits until one looks good. What it reveals: you are rescuing the result instead of reading it, and every unusual year you remove is a year the rule could not handle. The fix: the three cuts are written in the paragraph before the test, and the report shows every one of them, failing rows included. No other split is reported as the result.

Report In R, With The Null Beside It

A result line has a fixed shape. Without all of it, it is not a result.

Expectancy
The average result per trade in R: win % × average win − loss % × average loss. It is the one number that combines how often a rule wins with how much it wins and loses.

Here is why the win rate alone misleads. A made-up rule wins 62% of the time. Its average win is +0.5R and its average loss is −1.0R. Its expectancy is 0.62 × 0.5 − 0.38 × 1.0 = 0.31 − 0.38 = −0.07R. It wins most of the time and loses money doing it. A rule that wins 40% of the time can be far better. You only find out with all the fields.

FieldWhat it answers
nHow many trades the result rests on
Win %How often the rule won, never shown without the next three
Average win and average loss, in RHow much a win and a loss were worth
Expectancy, in RWhat one trade earned on average, after costs
Null expectancy, in RWhat the same rule earned on shuffled data
CutsThe same fields for each half, each year and the recent stretch

Everything is in R, net of the costs in your paragraph. Never dollars: a dollar result depends on the size you happened to trade, and R does not.

The rule: every result carries n, win %, average win, average loss, expectancy and the null's expectancy, in R, net of costs, for the whole sample and for every cut.

Getting it wrong looks like "68% winners" with nothing beside it, or a result in dollars from one account size. What it reveals: you are reporting the number that feels like success rather than the number that measures it. The fix: one report template with these fields, used for every test. A blank field means the line is an idea, not a result, and it is filed as an idea.

Two Gates: The Market, Then You

A test on market data answers one question: did the market behave this way, more than chance allows? It says nothing about whether you can collect on it. Those are two questions, so your register holds each idea to two gates, in order. These are a standard for your own record. They are thresholds, not results.

Gate 1 (Market Data)
The test of a locked rule on historical market data. It passes at n of at least 100 trades, beating a volatility-preserving null, positive in both halves and in each calendar year, plus a 2023–2026 recency check, reported in R with n, win %, expectancy and the null's expectancy.
Gate 2 (Own Execution)
The test of your own live trades of a rule. It passes at n of at least 30 live trades, across at least 20 distinct sessions, with expectancy of at least +0.3R after commissions. Sim trades never count toward it.

The session floor matters as much as the trade count. Thirty trades from four sessions is one week's conditions, not a sample: if those days trended, every trend rule looked good. Twenty distinct sessions is the minimum spread of days before your own record says anything about you.

The two gates are independent. A rule can pass the market test and fail yours, because you skip the signals that feel wrong or fill a few ticks worse than the backtest. A rule can look fine in your live trades on too few days for the market test to agree. An idea reaches the top label in your register only when it passes both; passing one leaves it at the middle label. And the label never rises above what the market test supports: good live trades do not lift an idea that has not passed Gate 1.

One limit is a fact about data, not about any rule. A rule built on order flow needs historical tick data with the aggressor side for every year it is tested on, and a platform's own short tick history does not provide that. Until you have the data, that rule cannot meet Gate 1's every-year requirement. That is a data block, not a failed test.

The rule: Gate 1 is passed on market data, Gate 2 on your own live trades, each recorded in its own column of the register, and an idea earns the top label only with both.

Getting it wrong looks like a strong backtest treated as permission to trade bigger, or thirty live trades from one good week counted as Gate 2. What it reveals: you are letting one question answer the other, usually because the answer you have is the one you wanted. The fix: two columns per register entry, Gate 1 and Gate 2, each filled only from its own source, with the session count written beside the trade count. Size does not move with either: it comes from your fixed base R, the stop and the grade table in Module 14.

Why Sim Never Measures Edge

Picture a buy limit resting at the PD Low. Price trades down, touches the PD Low exactly, and leaves 40 points higher. In live markets, there were buyers resting at that price before you, and the sellers who reached it may have filled every one of them and none of you. The trade that touches and leaves is often the best trade of the day, and it is the one you are least likely to get.

A simulator cannot see that queue. It has to guess where your order sat, and NinjaTrader's simulator offers a setting that fills simulation orders immediately instead of using its fill engine. Backtests have the same pressure: NinjaTrader's fill-on-touch option is described in its own documentation as "a more liberal fill algorithm for back-testing purposes only", and it is off by default. Leave it off. Either way, sim can hand you the fill on exactly the trades where a live fill was least likely.

That bias sits on the one variable that decides outcomes. Where in the level you get filled, and whether you get filled at all, is the skill gap between a right read and a good trade. A simulator that is generous on that variable measures the read and flatters the execution, so its expectancy is not your expectancy.

The rule: sim trades are counted and reported separately and are never pooled into any expectancy figure. Sim counts occurrences: how often the rule fired, and whether you saw it. It never measures edge. A funded evaluation account that runs on simulated fills is sim for this purpose, and market replay is fill practice, not evidence.

Getting it wrong looks like 18 live trades and 40 sim trades added together to "pass" a 30-trade threshold, or a sim result quoted as what a rule earns. What it reveals: you want the gate passed faster than your live record allows, and the sim fill is doing the work your execution has not done yet. The fix: keep sim and live in separate journal accounts. Every Gate 2 count is read from the live account only, and every count you write down carries its live/sim split beside it, so a pooled number cannot appear by accident.

The Label You Give It, And What Would Reopen It

Every idea in your register carries one of five labels, and the label comes from the tests, not from how you feel about the idea. The default for any idea is that it has no edge; a test exists to try to show that, and most ideas fail it. That is the test working.

UNTESTED
A label for an entry in your own register: the rule is written and locked, and has not yet been run against data.
WATCH
A label for an entry in your own register: the rule has been run and is positive, but unstable across halves or years, or rests on too few trades to read.
CANDIDATE
A label for an entry in your own register: the rule beats its null and is stable across both halves, every year and the recent stretch, but has not yet met the thresholds of both gates.
VALIDATED
A label for an entry in your own register: the rule has passed both gates, Gate 1 on market data and Gate 2 on your own live trades.
KILLED
A label for an entry in your own register: the rule failed its test. The entry keeps the reason it failed and a reopen condition, so it is never re-run blind and never stays dead by accident.
Reopen Condition
The specific new evidence or new rule that would justify testing a failed idea again, written into its register entry at the moment it fails. A reopened idea is a new entry, tested from scratch.

The last label is where the psychology lives. You will like some ideas. Some of them will fail, and the pull to keep a liked idea alive is strong: one more filter, one more year left out, one more run with the stop moved. A failed idea that is rerun with a tweak under its old number is no longer a test; it is a search. So when an idea fails, its entry records two things while you still have no reason to want it back: why it failed ("stop sat inside the noise", "opposite signs in the two halves", "no better than the null") and what would reopen it ("a different stop, tested from scratch as a new entry"). Some failures have no reopen condition. Write that too.

The rule: the label follows from the gates and the cuts, by the definitions above, and a failed idea keeps its reason and reopen condition and comes back only as a new entry.

Getting it wrong looks like an idea moved up a label after three good live days, or a failed idea quietly rerun with a new stop under its old number. What it reveals: the label has become a measure of your attachment rather than of the evidence, and a label that bends to attachment stops protecting you from it. The fix: each label has its condition written at the top of your register, and you change a label only at the scheduled review, by reading the conditions against the report, never mid-week and never after a result. The reason and reopen fields are mandatory on a failed entry; a blank one means the entry is not finished.

An edge is what a locked rule earns after costs above its block-shuffled null, reported in R, and it counts only when the rule stays positive in both halves, every year and the recent stretch. Your own live record, never sim, is a separate test of whether you can collect it.

Worked Case: One Register Entry, Start To Finish

Illustration · not a trade record

An invented register entry, built to show the steps in order. The rule below was made up for this page. It is not a rule, setup or trigger from this course, it uses no level, and the dataset summary is invented: the numbers are round on purpose so you can check every one of them. It belongs to no one.

Entry 7: the Three Lower Lows rule (invented). Locked paragraph, written and dated before any data was opened: "MNQ, 5-minute bars built from 1-minute data. Between 10:00 and 11:30 ET, when three consecutive 5-minute bars each make a lower low than the bar before and each close below their open, go long on the third bar's close, with the entry's tick of slippage charged beyond that close. Stop: 1 tick below the third bar's low. Target: the high of the first of the three bars. One trade per session. Any trade still open at 12:00 ET is scored at that price. Data: January 2019 to June 2026. Costs: one round-turn commission and one tick of slippage per side, in R. Null: the same rule on 1-minute returns shuffled within 30-minute blocks, 200 shuffles, averaged. Cuts: halves by trade count, each calendar year, 2023–2026."

Note the entry. The third bar's close is known the moment the bar closes, and an order sent on that close uses nothing it could not have had, so it is not lookahead. What a test cannot assume is a fill at exactly that price, so the paragraph charges its tick of entry slippage beyond the close. An entry at the third bar's low, inside that bar, would be lookahead: the low is only known once the bar is over.

Whole sample. n 240 trades. 108 winners: 45%. Average win +1.5R, average loss −0.9R (losses average less than 1R because some trades are scored at 12:00 before reaching the stop). Expectancy: 0.45 × 1.5 − 0.55 × 0.9 = 0.675 − 0.495 = +0.18R. Null: 40% winners, average win +1.4R, average loss −0.9R, so 0.40 × 1.4 − 0.60 × 0.9 = 0.56 − 0.54 = +0.02R. The rule beats zero by 0.18R and beats random by 0.16R. Only the second number is the rule's.

Halves. Trades 1 to 120 (January 2019 to late 2022): 55 winners, 46%, +0.21R, null +0.02R. Trades 121 to 240: 53 winners, 44%, +0.14R, null +0.02R. Same sign, both above the null. (Check: the two equal halves average (0.21 + 0.14) ÷ 2 = 0.175, which rounds to the whole sample's +0.18R.)

Met, on this invented data. Gate 2: no live trades yet. Not started. Sim occurrences, if any, are logged as a count only.

Label: CANDIDATE. Reason: Gate 1 met; Gate 2 not started, and either gate alone keeps the entry here. Reopen condition: none needed at this label. The backtest stays an upper bound: it took every signal, at the stated price, without hesitation.

Hypothetical illustration. Hypothetical results have inherent limits: they are not actual trading and do not reflect real fills, slippage or the pressure of risk, and no representation is made that any account will achieve similar results.

Notice what decided the label. Not the +0.18R: a rule can show that and still fail, because the null, the halves, a single bad year or the recent stretch can each take it down. And not the trader's opinion of the idea, which never appears in the entry at all. Every line the label rests on was decided in the paragraph before the data was opened.

Check Any Backtest In Six Lines

Use this on any backtest you have run, or any you have read. Score one point for each line that is true.

  1. Locked. The rule, entry, stop, target and window were written and dated before the data was opened, and the test ran exactly that.
  2. Null. The result is shown beside the same rule's result on volatility-preserving shuffled data, not beside zero or 50%.
  3. Halves. Both chronological halves are reported, each with its null beside it, and both are positive.
  4. Years and recency. Every calendar year is reported, failing years included, plus the recent stretch on its own, all positive.
  5. The report. n, win %, average win, average loss, expectancy and null expectancy are all given, in R, net of costs.
  6. Fills. Limit orders were not filled on a touch, no sim trades are pooled into the result, and any live record is counted separately from it.

Lines 1 and 2 override the score. If either is false, the backtest is an idea, not a result, however good the rest looks: without the lock it is a fit, and without the null there is nothing it beat. 6 of 6: it is evidence for the market half of the question, and only that; your own live record is still a separate test. 4 or 5: it is incomplete; the missing lines are what you run or ask for next, before it changes anything you do. Under 4: treat it as an idea worth writing a locked paragraph for, and nothing more.

Before Your Next Session

Apply This Now

Pick one idea you already believe in. Write its locked paragraph: the rule, the entry, the stop, the target and the window, in one paragraph, with today's date and an entry number. Do not open a chart for it. That's the whole assignment.
